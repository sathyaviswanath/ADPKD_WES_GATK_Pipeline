# Troubleshooting Guide

This document summarizes the major issues encountered while developing the ADPKD Whole Exome Sequencing (WES) pipeline and the solutions used to resolve them.

---

# 1. Storage Limitations (GitHub Codespaces)

## Problem

GitHub Codespaces has limited disk space. Running a complete WES pipeline can quickly exhaust the available storage due to large FASTQ, BAM, and reference genome files.

## Solution

To reduce storage usage:

- Downloaded only chromosomes **4** and **16** (PKD1 and PKD2 regions).
- Removed intermediate SAM and BAM files after downstream processing.
- Deleted raw FASTQ files after trimming and quality control.
- Retained only the essential VCF files required for variant analysis.

---

# 2. Docker Permission Error During VEP Cache Installation

## Problem

The VEP cache installation failed with:

```text
Permission denied
```

or

```text
Cannot open Local file
```

## Cause

Docker containers did not have permission to write into the mounted VEP cache directory.

## Solution

Changed the ownership of the VEP directory:

```bash
sudo chown -R $USER:$USER Resources/VEP
```

Then reran the Docker installation.

---

# 3. VEP Cache Download Failed

## Problem

VEP could not locate the cache or attempted to download files repeatedly.

## Cause

Incorrect cache location or missing Docker volume mapping.

## Solution

Mounted the local cache directory correctly:

```bash
docker run --rm \
-v $PWD:/data \
-v $PWD/Resources/VEP:/opt/vep/.vep \
ensemblorg/ensembl-vep
```

Verified the cache installation before running annotation.

# 4. Duplicate Candidate Variants

## Problem

Multiple rows represented the same genomic variant because VEP reports one row per transcript.

## Cause

A single variant may affect several transcripts.

## Solution

Retained only variants from:

- Canonical transcripts
- MANE Select transcripts

This reduced duplicate entries while preserving the most biologically relevant transcript.

---

# 5. Variant Prioritization Order

## Problem

The generated candidate variant table was not sorted according to clinical importance.

## Solution

Created a custom priority score based on:

- HIGH impact
- MODERATE impact
- Interpretation
- gnomAD allele frequency

Then sorted the dataframe before exporting:

```python
sort_values()
```

This places the strongest candidate variants at the top of the report.

---

# 6. Clinical Interpretation

## Problem

Automatically assigning interpretation solely from one annotation source can be misleading.

## Solution

Combined multiple criteria:

- Consequence
- Impact
- PolyPhen
- gnomAD allele frequency

Examples:

- High-impact loss-of-function variant; Strong Candidate Variant
- Rare damaging missense variant; High Priority Candidate
- Common population variant; Lower Priority Candidate

---

# 7. Cleaning the Repository Before Uploading

## Problem

The project directory contained many large intermediate files that were unnecessary for sharing on GitHub.

## Solution

Removed:

- VEP cache
- ANNOVAR databases
- Intermediate alignment files
- Temporary annotation files

Retained:

- Final VCF files
- Annotation tables
- Figures
- Python scripts
- Documentation
- Final reports

A `.gitignore` file was added to prevent large temporary files from being committed.

Documenting these issues improves the reproducibility of the pipeline and provides a useful reference for future analyses.
